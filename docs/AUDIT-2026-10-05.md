# Pipeline, data and architecture audit (5 Oct 2026)

Why: shot one's arms score near zero (coffee Q = 0 for both arms; shoes mean Q ≈ 0.04–0.05),
and the 12-pair shoes A/B is not significant (ΔQ +0.008, p = 0.81). Before spending more,
check whether something in the pipeline holds both arms down.

## 1. Train ↔ serve contract: consistent

Both paths go through the same openpi `LeRobotB1KDataConfig` (`create_trained_policy`
rebuilds it at serve time), so these match by construction. Each was checked in code:

| Item | Training | Serving | Verdict |
|---|---|---|---|
| Cameras | image_0 = head (zed), image_1 = left wrist, image_2 = right wrist, via `robot_config.observations` | same dict, same order | ✅ |
| Robot state | `B1KInputs.extract_state_from_proprio` on `observation.state` (full proprio; training would crash at index 53 otherwise) | same function on the evaluator's proprio | ✅ |
| Actions | `MappedDeltaActions` → model → `MappedAbsoluteActions` | same pair | ✅ |
| Normalisation | one stats file for both arms, z-score (`use_quantile_norm=False`) | served from `assets/<first task id>` via `ASSET_ID` (fixed 2 Oct) | ✅ |
| Prompt | `prompt_from_task` → task NAME from `meta/tasks.parquet` | patch 0003 registers name → name; checked before every eval (fixed 3 Oct) | ✅ |
| Depth streams | dropped (never read by the model) | not sent | ✅ |
| Serving stack | — | released baseline scores Q = 0.111 through it | ✅ validated |

## 2. Data usage: the arms are badly undertrained

| | Released baseline (`pi05_b1k`) | Shot one arms |
|---|---|---|
| Steps × batch | 50,000 × 32 = 1.6 M samples | 10,000 × 32 = 0.32 M samples |
| Training data | 1 task, ~0.43 M frames | 2 tasks, ~2.75 M frames |
| **Passes over the data** | **~3.7** | **~0.12** |
| VLM backbone | trained (full finetune) | **frozen** (memory) |
| Initialisation | `pi05_base` | `pi05_base` |
| Outcome | 11% success on its task | no success; Q ≈ 0.04 on shoes |

Each training frame was seen ~30× less often than in the baseline, with the visual backbone
frozen. A policy at the floor cannot show an A/B effect, so this is the main reason the
experiment is uninformative, not a wiring bug.

## 3. Statistics: one attempt per instance is too noisy

Shoes Q takes values in {0, 0.1, 0.2}, and the two arms score on *different* instances.
With m = 1 the run-to-run simulator noise dominates (paired SE 0.034 at n = 12). Phase 2
(both arms, instances 22–36, running now) completes n = 27 and gives the variance estimate
that sizes the next evaluation.

## 4. Plan for a result that can be significant (shot two)

1. **Initialise both arms from the released `pi05_b1k` checkpoint**, already adapted to
   this robot and BEHAVIOR's visuals, instead of `pi05_base`. The launcher now has
   `--init-from` (arm B's progress head still initialises fresh via `missing_regex`).
   Same weights for both arms keeps the A/B fair.
2. **Train on shoes only**: the task with signal. Coffee is at the floor. Twice the
   steps per task for the same cost.
3. **Train longer:** 20k steps per arm, ~0.4 passes over shoes from a BEHAVIOR-adapted
   start. That's ~20.5 h per arm ≈ $15 per arm.
4. **Evaluate with m = 2 attempts per instance** on n = 27 shoes instances, both arms: 108
   attempts × ~16 min ≈ 29 h ≈ $21. Rules fixed before the run: paired ΔQ on
   per-instance means, 95% CI; no re-running until significant.

Estimated cost ≈ $51 + margin. Time ≈ 41 h training + 29 h evaluation ≈ 3 days, so it
must start by ~8 Oct for the 16 Oct deadline.
